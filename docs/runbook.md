# Incident Response Runbook (1-page)

**Applies to:** Student Registration Web Application (IFT 542 hardened build).
**Severity guide:** SEV1 security breach / data loss · SEV2 outage · SEV3 degraded.
**Escalation:** Peter Adeshina (peteradeshina3@gmail.com) → course instructor.

## 1. Preparation
- Run in the authorised lab only (`localhost`, fictitious data). Never connect a
  real university database or PII.
- Source of truth: `Makefile` (`make setup build up down reset clean evidence`).
- Evidence output is written to `evidence/generated/` — do not edit these files;
  they are regenerated by `make tests`.

## 2. Identification
- Detect: `docker compose logs app --since 24h` (JSON audit log, redacted secrets).
- Look for: repeated 401/403/429 entries, `auth_failed` floods, CSRF rejections,
  blocked SSRF attempts, unexpected admin actions.
- Confirm: `bash tests/run.sh` and compare with the last `evidence/generated/` run.

## 3. Containment
- Immediately isolate: `docker compose stop app vulnerable` (keep `db` up if logs
  are needed, otherwise `docker compose stop`).
- Block a specific attacker IP at the firewall; if a user account is suspected,
  `docker compose exec` the CLI (`docker compose run --rm cli php reset.php <email> --lock`)
  or disable the account from admin → Users → Lock.
- Freeze evidence: copy `evidence/generated/` and `logs/app.log` to a timestamped
  quarantine folder; never delete during an incident.

## 4. Eradication
- Remove the cause: fix the vulnerability in `app/`, then rebuild and reseed:
  `make clean && make build && make up && make seed` (wipes and recreates both DBs).
- Reset any affected credentials; rotate the admin password (`db/seed-output/ADMIN_PASSWORD.txt`).

## 5. Recovery
- Re-enable services: `docker compose start app`; run `make smoke` and the full
  `make tests`; confirm 0 failures before announcing recovery.
- Re-verify residual-risk acceptances in `docs/risk-register.md` are still valid.

## 6. Lessons learned
- Within 24h file an incident record in `docs/incidents/` (or the report appendix):
  timeline, root cause, evidence files, controls that worked/failed, and one
  action item. Update the risk register L/I scores if exploitability changed.

---
*Ethics note: activity is authorised, local-only, and uses fictitious data. Do not
carry any technique from this exercise to systems you do not own or are not
explicitly authorised to test.*
